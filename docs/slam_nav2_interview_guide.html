SLAM / Nav2 与本仓库导航底层

0. 30 秒定位：我做了什么

口述模板： 「我做的是两轮平衡车的底层运动控制。上层如果以后接 Nav2，它输出的是标准 /cmd_vel；我这边负责把 Twist 安全地落到力矩控制： 线速度走速度环/位置环，角速度走偏航环，再和平衡力矩做差动混合。 也就是说，我做的是 Nav2 Controller 之下、电机驱动之上的那一层。」
已完成本仓库实际工作 串级 / LQR 平衡、斜坡前馈、MotionCommandAdapter、 YawLoop（含航向保持）、PositionLoop、WheelMixer、 SafetyLimiter、Gazebo 仿真。
未集成SLAM / Nav2 本体 无激光/深度建图节点、无 map→odom→base_link 完整定位树、 无 costmap / BT Navigator / Planner Server。RViz 的 Goal Pose 插件存在但无订阅者。
面试时务必先讲清边界：不要把「轮式位置环 / 航向保持」说成「地图定位 / 全局导航」。 诚实 + 能讲清楚对接缝，反而加分。

1. 移动机器人软件分层

把整条栈从上到下讲清楚，再落到本仓库，面试官很容易跟上。

┌──────────────────────────────────────────────────────────┐ │ 任务层 / 应用层 多点巡航、任务编排、业务逻辑 │ ├──────────────────────────────────────────────────────────┤ │ 导航规划层 Nav2 BT · 全局规划 · 局部规划 · 恢复行为 │ ├──────────────────────────────────────────────────────────┤ │ 感知与建图 SLAM 激光/视觉建图 · 定位 · TF · /map │ ├──────────────────────────────────────────────────────────┤ │ 运动接口 /cmd_vel Twist(v, ω) —— 行业标准「接缝」 │ ├──────────────────────────────────────────────────────────┤ │ ★ 本仓库重点 平衡 + 速度/位置环 + 偏航 + 力矩混合 │ ├──────────────────────────────────────────────────────────┤ │ 驱动与仿真 ros2_control · Gazebo · IMU · 轮关节 │ └──────────────────────────────────────────────────────────┘
关键认知：/cmd_vel 是 Nav2 与底盘控制的解耦接口。 本仓库已经把这层接好了，所以「缺的是上面的建图定位与规划，不是运动协议」。

2. SLAM 框架（面试通识）

SLAMSimultaneous Localization and Mapping：一边建地图，一边估计自己在地图中的位姿。

2.1 经典流水线

传感器(LiDAR/相机/IMU) │ ▼ 前端（Front-end） · 特征提取 / 扫描匹配（ICP、NDT、scan-to-map） · 帧间里程计（相对位姿） │ ▼ 后端（Back-end） · 位姿图优化 / 滤波（EKF、图优化 g2o/Ceres） · 回环检测（Loop Closure）抑制漂移 │ ▼ 地图输出 · 2D 占用栅格 OccupancyGrid（Nav2 最常用） · 或 3D 点云 / TSDF │ ▼ 定位模式 · Mapping：边建边定位 · Localization-only：已有地图 + AMCL / 粒子滤波 / scan match

2.2 ROS 2 常见方案

方案特点面试怎么说
slam_toolbox 2D 激光主流；支持 lifelong / 序列化地图 室内差速底盘首选之一
Cartographer 子图 + 回环；2D/3D 强调图优化与子图思想
视觉 SLAM（ORB-SLAM 等） 依赖纹理与光照；可融合 IMU 说明与激光的互补性
robot_localization / EKF 多源融合（轮速+IMU+GPS） 常放在里程计层，不是完整 SLAM

2.3 面试必提的 TF 树

map ──(SLAM / AMCL 慢变校正)──► odom ──(轮速/IMU 里程计)──► base_link │ │ │ 全局一致，可跳变修正 │ 连续平滑，短期可靠、长期漂移 ▼ ▼ Nav2 全局代价地图用 map 局部控制、短时预测常用 odom
一句话：「odom 负责连续，map 负责全局不漂；SLAM/定位节点发 map→odom，底盘里程计发 odom→base_link。」

2.4 与本仓库的关系

  • 当前传感器：Gazebo IMU + 轮关节；没有激光/深度用于建图。
  • 文档明确：斜坡估计用 /joint_states 轮速，不依赖 DiffDrive 里程计当「真相」。
  • PositionLoop 里的「位置」是轮弧长积分，用于停车回位，不是地图坐标系定位。

3. Nav2 框架（面试通识）

Nav2ROS 2 导航栈：把「目标位姿」变成一串安全的 /cmd_vel。

3.1 核心组件

组件职责常见算法
BT Navigator 行为树编排：规划→跟踪→失败恢复 XML 行为树，可插 Recoveries
Planner Server 全局路径（map 坐标系） NavFn、Smac、Theta*
Controller Server 局部跟踪，输出 Twist DWB、MPPI、RPP、TEB（插件）
Smoother 路径平滑 简单平滑 / Constrained smoother
Costmap 2D 障碍膨胀、动态层 static / obstacle / inflation / voxel
AMCL / 定位 已知地图下粒子滤波定位 常与 map_server 配合
Behavior / Recovery 卡住后的自救 原地旋转、后退、清 costmap

3.2 典型数据流

/goal_pose 或 NavigateToPose action │ ▼ BT Navigator ├─► compute_path_to_pose → 全局路径 (Path) ├─► follow_path → Controller → /cmd_vel └─► 失败？ → backup / spin / wait → 再规划 │ ▼ 底盘（本仓库 balance_controller）执行 Twist

3.3 全局 vs 局部

全局规划 在整张地图找一条可行路径；更新慢；关心连通性与最优性。
局部控制 在机器人附近滚动窗口跟踪路径、躲动态障碍；输出实时 v/ω；更新快（几十 Hz）。

3.4 Costmap 面试要点

  • Static layer：来自 /map
  • Obstacle layer：激光/点云即时障碍
  • Inflation layer：按机器人半径膨胀，保证安全距离
  • 全局 costmap 多挂在 map；局部 costmap 多挂在 odom

4. 本仓库：我改的导航部分（重点讲）

这里的「导航」= 可被上层导航栈驱动的运动框架， 对应文件主要在 src/balance_car_control/src/。

4.1 总览：从 Twist 到左右轮力矩

/cmd_vel Twist{linear.x, angular.z} │ ▼ MotionCommandAdapter ← 你加的「协议适配 + 安全」 · 限幅、单位换算、超时归零 · v[m/s] → wheel_v[rad/s] = v / r · ω[rad/s] → target_yaw_rate │ ├──────────────────────────────┐ ▼ ▼ PositionLoop（可选） YawLoop（你重点改的方向通道） x_target 积分指令轮速 · |ω|大：角速度 PD → turn_tau 输出 v_setpoint · |ω|≈0：航向保持（锁定 yaw） │ │ ▼ │ VelocityLoop / LQR │ → pitch_target / balance_tau │ │ │ └──────────┬───────────────────┘ ▼ WheelMixer left = balance − turn right = balance + turn │ ▼ SafetyLimiter → /wheel_effort_controller/commands

4.2 MotionCommandAdapter —— Nav2 接缝

文件：motion_command.py

  • 只做适配，不写控制律（职责清晰，面试好讲）。
  • cmd_vel_timeout_sec（默认 0.5 s）无新指令 → 目标归零 → 车回到站立。
  • 线速度、角速度、换算后轮速三重限幅，防止上层乱指令打翻车。
# 单位约定（面试可直接背）
cmd_vel.linear.x  [m/s]  → target_wheel_velocity = v / wheel_radius
cmd_vel.angular.z [rad/s] → target_yaw_rate = ω
# 例：0.1 m/s，r=0.0325 m → 约 3.08 rad/s

4.3 YawLoop —— 你改动最大的「导航相关」逻辑

文件：yaw_loop.py。不是简单的角速度 P，而是双模式：

模式进入条件行为
主动转向 |target_yaw_rate| ≥ yaw_cmd_activate_threshold 松开航向锁；角速度 PD 跟踪 cmd_vel.angular.z
航向保持 近似直行（角速度指令很小） 进入瞬间锁定当前 yaw；外环 yaw→rate_cmd，内环仍走角速度 PD
为什么要航向保持？ 平衡车直行时，轮子不对称、地面摩擦、IMU 噪声会导致缓慢偏航。 没有 heading hold，长距离「直线」会漂；有了它，相当于在底盘层做了简易航向闭环， 减轻上层导航的负担。 
# 直行时（伪代码）
if turning:
    yaw_ref = None
    turn_tau = PD(target_yaw_rate - yaw_rate)
else:
    if yaw_ref is None: yaw_ref = yaw          # 进入瞬间锁定
    yaw_error = wrap_pi(yaw_ref - yaw)
    rate_cmd = clamp(kp_heading * yaw_error, ±max_heading_rate)
    turn_tau = PD(rate_cmd - yaw_rate)
  • wrap_pi：角度误差折到 (-π, π]，避免 ±180° 附近跳变。
  • yaw_rate_deadband：抑制陀螺噪声在站立时乱打差动力矩。
  • max_turn_tau 必须明显小于平衡力矩预算，否则转向会「抢走」直立所需力矩。

4.4 PositionLoop —— 容易被误称为「定位」

文件：position_loop.py。三环最外环：位置 → 速度 → 倾角 → 力矩。

要解决的真实问题：纯速度环停车时，车会先后仰刹车，轮子倒退一点； 速度归零后停在新位置。位置环积分「被命令的轮速」得到 x_target， 把倒退量拉回去——这是轮坐标系行程伺服，不是 SLAM 定位。
v_cmd = 0 → x_target 冻结 → 拉回倒退量 → 停在原地 v_cmd ≠ 0 → x_target 随指令前进 → 帮助跟踪行程 v_setpoint = v_cmd + v_corr(位置误差)

4.5 WheelMixer —— 平衡优先的差动分配

left  = balance_tau - turn_tau
right = balance_tau + turn_tau
# 同向分量 = 直立/加速；反向分量 = 转向

面试加分点：说明「若 |balance|+|turn| 超过单轮饱和，会出现一边转向失效」； 工程上用 max_turn_tau 预留平衡预算，而不是事后再抢。

5. 设计决策与踩坑点（体现思考深度）

Q：为什么转向不直接改 pitch_target？
A：俯仰是直立自由度，转向应走差动力矩。改 pitch 会和平衡环抢同一控制量，耦合难调。 我们让速度通道改 pitch、方向通道改 turn_tau，物理上解耦。
Q：为什么 /cmd_vel 要超时归零？
A：导航节点或遥控掉线时，如果继续执行最后一帧速度，车会失控冲出。 超时归零是移动机器人底盘层的基本安全契约，Nav2 也假定底盘具备这种行为。
Q：平衡车接 Nav2 和普通差速车差在哪？
A：普通差速车几乎「有速度指令就能走」；平衡车必须先保证倒立摆稳定。 所以 Controller 输出的 v/ω 不能过大，且底盘要把力矩预算优先留给平衡。 斜坡场景还要倾角前馈，否则 Nav2 以为在平地跟踪路径，实际会栽坡上。
Q：PositionLoop 能代替 odom 吗？
A：不能。它只在轮坐标系里做短时行程闭环，没有全局一致性，也不处理打滑与地图。 真正的导航仍需要里程计话题 +（可选）SLAM/AMCL 提供的 TF。

6. 如何接到真正的 Nav2（体现完整视野）

面试官常问「下一步怎么做」。按依赖顺序答：

  1. 传感：加 2D LiDAR（或深度相机），发布 LaserScan/PointCloud2。
  2. 里程计：由轮速 + IMU 发布 nav_msgs/Odometry 与 odom→base_link TF （可考虑 robot_localization）。
  3. 建图：slam_toolbox 出图；保存后用 map_server + AMCL 定位。
  4. Nav2 bringup：配置 footprint（两轮车近似矩形/圆形）、最大 v/ω 与本仓库限幅一致。
  5. 保持本仓库不动：Nav2 Controller 直接往 /cmd_vel 发即可。
slam_toolbox / AMCL │ map↔odom ▼ Nav2 (planner + MPPI/DWB) │ /cmd_vel ▼ balance_controller（已完成）→ 轮力矩
参数对齐很关键：Nav2 的 max_vel_x / max_vel_theta 应 ≤ 本仓库 max_linear_velocity / max_angular_velocity， 否则上层以为能转，底盘已被削顶，路径跟踪会振荡。

7. 面试问答速查

概念

SLAM 前端和后端分别做什么？
前端做帧间关联与相对运动估计；后端做全局优化与回环，抑制累计误差。
map 和 odom 坐标系有什么区别？
odom 连续短期准、长期漂；map 全局一致、定位修正时可能跳变。Nav2 全局规划看 map，局部控制常看 odom。
Nav2 里 Planner 和 Controller 的区别？
Planner 出全局路径；Controller 在局部窗口跟踪路径并输出 /cmd_vel，同时处理近距障碍。

结合本项目

你在导航相关部分具体改了什么？
接入标准 /cmd_vel；实现 MotionCommandAdapter（换算/限幅/超时）； YawLoop 角速度跟踪 + 直行航向保持；PositionLoop 解决停车倒退； WheelMixer 保证转向不抢平衡力矩。
为什么说你的接口已经 Nav2-ready？
因为消费的是 geometry_msgs/Twist，话题名 /cmd_vel，语义与差速底盘一致； Nav2 Controller Server 无需改协议即可对接。缺的是传感器、TF 与 Nav2 进程本身。
调参顺序怎么做？
先无指令站稳 → 小线速度标定速度通道 → 小角速度标定 kp_yaw / max_turn_tau → 开航向保持看直行漂移 → 最后组合弧线；再考虑接上层规划。

8. 一分钟收尾话术

「总结一下：我熟悉 SLAM 的前端匹配、后端优化、回环和 map/odom TF 分工； 也熟悉 Nav2 的行为树、全局规划、局部控制和 costmap 分层。 在当前两轮平衡车项目里，我把重心放在更难的底层——先让倒立摆在斜坡上稳， 再提供与 Nav2 兼容的 /cmd_vel 运动层，特别做了偏航跟踪、航向保持、停车位置环和力矩预算分配。 下一步只需要补上激光、里程计 TF 和 Nav2 bringup，就能把完整导航跑通。」
